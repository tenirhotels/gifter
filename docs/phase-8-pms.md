# Фаза 8: бронь по PMS (Hotel Hub / Exely)

Gifter подтверждает номер брони по PMS. Источник — **на выбор** (страница «Подключение к PMS»), ответ у обоих в формате Exely `{"booking": {...}}` и разбирается одним кодом. Gifter только читает; брони в PMS не создаёт.

| | Hotel Hub (свой сервис) | Exely напрямую |
|---|---|---|
| Запрос | `GET {адрес хаба}/v1/properties/{код}/bookings/{номер}` | `GET https://connect.hopenapi.com/api/read-reservation/v1/properties/{propertyId}/bookings/{номер}` |
| Вход | токен хаба с правом `bookings` | OAuth: `client_id` + `client_secret` → `POST /auth/token` (client_credentials), токен 15 минут, Gifter кеширует и обновляет сам |
| Что в настройках | адрес, код отеля, токен | идентификатор отеля, client_id, client_secret (адрес — по умолчанию connect.hopenapi.com) |
| Статус комнат | `roomStays[].hub.status`, возраст данных `hub.stale` | нет (статус брони Active/Cancelled) |
| 503 «данные устарели» | да | нет |
| Где взять доступ | хаб: «API и токены» | Exely: «Настройка гостиницы → Подключение API»; доступ к Read Reservation API включается отдельно |

Описание API хаба — `docs/bookings-api.md` в репозитории Hotel Hub (право токена `bookings`).

## Решения владельца

| Вопрос | Решение |
|---|---|
| Объём | Проверка брони при внесении. Фоновая сверка, заезд и использование по статусам PMS — следующие шаги |
| Нет брони / хаб недоступен | **Всегда строго:** без подтверждения PMS бронь не сохраняется |
| Подключение | Страница в панели «Администрирование → Подключение к PMS»; токен хранится зашифрованным и не показывается |

## Подключение

1. Выбрать источник и получить доступ: хаб — токен с правом `bookings`; Exely — ключи подключения (client_id, client_secret).
2. В Gifter (администратор): Администрирование → «Подключение к PMS» → источник, поля выбранного источника, «Проверять брони по PMS» → «Сохранить» → «Проверить связь» (запрашивается несуществующая бронь; «не найдена» — связь и ключи в порядке).
3. Пустое поле токена или client_secret при сохранении оставляет прежнее значение. Секреты хранятся зашифрованными и не показываются; смена настроек пишется в журнал аудита (секреты — только факт смены).
4. Переключение между источниками — сменой выбора и сохранением; сохранённые брони не меняются.

Пока подключение выключено, бронь вносится вручную, как в фазе 6.

## Как вносится бронь

Front Office вводит **только номер брони**. Gifter запрашивает PMS и показывает гостя, даты, число комнат и совпадение имени; после «Сохранить бронь» гость и даты берутся из PMS (введённое руками не используется).

- **Гость:** из гостей действующих комнат и заказчика брони берётся тот, кто совпал с получателем сертификата, затем с заказчиком сертификата; иначе — несовпадение (нужна причина, бронь уходит на проверку Финансов, как в фазе 6).
- **Даты:** заезд — самый ранний, выезд — самый поздний по действующим комнатам; отменённые комнаты не учитываются. Даты должны попадать в срок сертификата.
- **Бронь отменена в PMS** (все комнаты) — привязать нельзя.
- **Данные хаба устарели** (`hub.stale: true`) — бронь найдена, сохраняется с пометкой «данные устарели N мин» в истории и в карточке.
- Бронь по исключению для истёкшего сертификата проверяется так же.
- В карточке сертификата у номера брони: «Подтверждена по PMS (дата, возраст данных)» или «Внесена вручную».

## Сверка брони с сертификатом (19.10.2026)

При вводе номера форма показывает результат сверки (✓ / ✗) по пунктам. Есть расхождения — причина обязательна, бронь уходит на согласование Финансам с перечнем расхождений и причиной (они записываются в причину брони и в историю).

| Пункт | Правило |
|---|---|
| **Заезд** | в сроке действия сертификата — иначе бронь не принимается (причина не поможет: срок меняет менеджер, или бронь по исключению) |
| **Ночи** | число ночей в брони (выезд − заезд) не больше ночей в составе сертификата: услуги «ночь» пакета плюс доп. ночи. Сертификат на 1 ночь — заезд и выезд на следующий день; 1 ночь + доп. ночь — не больше 2 ночей. Больше — расхождение; меньше — нет. Если в составе нет услуги «ночь», ночи не сверяются |
| **Имя гостя** | совпадает с получателем или заказчиком сертификата; иначе расхождение |

**Имя при несовпадении.** Если имя гостя не совпало ни с получателем, ни с заказчиком, показывается и хранится только имя и первая буква фамилии («Bekki R.»): полные данные чужого гостя в Gifter не попадают — в форме, карточке, очереди Финансов, истории и аудите.

## Ошибки (бронь не сохраняется)

| Ответ PMS | Сообщение сотруднику |
|---|---|
| 404 `not_found` | Бронь не найдена в PMS — проверьте номер. Хаб держит окно броней: очень старая или далёкая бронь может быть в Exely, но не у хаба |
| 503 `source_unavailable` | Данные PMS устарели (нет связи с Exely) — попробуйте позже; «не найдена» не говорим |
| сеть, таймаут, 5xx | PMS недоступна — попробуйте позже |
| 401 / 403 | Хаб: токен отклонён (нет права `bookings`). Exely: ключи отклонены или нет доступа к Read Reservation API — к администратору |
| 400 | Номер брони PMS не принимает |
| 429 | Лимит (хаб: 120 запросов в минуту на токен; Exely: запрос токена 15 в минуту на IP) — подождать минуту. Подсказка в форме кешируется на 30 секунд, токен Exely — на 14 минут |

## Заезд по PMS (19.10.2026)

В день заезда Gifter повторно запрашивает PMS, чтобы убедиться в брони и не вносить заезд вручную. Запросов мало и только по делу (заселение в отеле в 15:30):

| Когда | Что | Кто |
|---|---|---|
| **08:00** | расхождения: бронь не отменена, даты и гость не изменились, условия сертификата соблюдены | автоматически |
| **16:00** | заселились ли: хаб отдаёт `checked_in` — заезд отмечается сам | автоматически |
| **19:00** | только те, кого в 16:00 не нашли заселёнными (поздний заезд) | автоматически |
| по кнопке «Заезд» | та же свежая проверка; без поля комментария | Front Office |

- Запросы только по сертификатам «Забронирован» с заездом **сегодня**, по подтверждённой PMS брони; за дни до заезда запросов нет. Один запрос на номер брони (общая бронь группы), пауза между запросами, не чаще раза в 2 часа на бронь. Заселённых, отменённых и снятых на проверку больше не опрашивают. Просроченные заезды — один запрос в день в 08:00. Раньше даты заезда кнопка отвечает «Заезд по брони — с …» без запроса.
- **Даты или гость изменились в PMS, условия соблюдены:** даты обновляются по PMS, запись в истории, проверки Финансов нет.
- **Бронь отменена в PMS или нарушены условия** (имя, ночи): заезд не отмечается, бронь уходит Финансам («Бронь изменена в PMS» с причиной), у Front Office — «Заезды: нужно внимание».
- **PMS недоступна:** ничего не меняется, отметка «PMS недоступна», повтор по расписанию.
- **Прямой Exely** статус заселения не отдаёт: автоматически заезд не ставится, остаётся кнопка «Заезд» с проверкой. Автозаезд — только через Hotel Hub (`roomStays[].hub.status`).
- Время запусков — `config/gifter.php` → `pms.arrival_check_times`; нужен тот же cron `schedule:run` раз в минуту. Команда: `gifter:sync-arrivals --slot=morning|afternoon|evening`.
- В карточке сертификата у номера брони: время последней проверки и итог.

## Формат номера брони

Номер проверяется в Gifter **до запроса** в PMS: `ГГГГММДД-код отеля-номер` (например, `20261019-9305-1266607523`), дата существует, код отеля совпадает с настройкой. Пробелы, невидимые знаки и «умные» тире из копирования приводятся к обычным автоматически. Неверный номер в PMS не отправляется — API не нагружается.

## Автоотметка «Использован» после выезда

Решение владельца (19.10.2026): гасить по `checked_out` от Hotel Hub; пока хаб не подключён (прямой Exely) — на следующий день после планового выезда с проверкой брони.

- Команда `gifter:sync-departures`, раз в день в 14:00 (`gifter.pms.departure_check_time`; выезд в отеле до 12:00), тот же cron `schedule:run`.
- Берутся сертификаты «Используется» с подтверждённой PMS бронью и плановым выездом: Hub — сегодня или раньше, Exely — вчера или раньше. Один запрос на номер брони, недавно проверенные (2 часа) и уже решённые (расхождение, спор) пропускаются.
- Свежая проверка брони: отмена или расхождение — не гасим, бронь уходит Финансам. Hub: гасим, когда все комнаты `checked_out`; если гость продлил проживание, ждём. Exely: плановая дата выезда прошла и бронь не изменилась — гасим.
- Есть невыполненные заявки по услугам — автоматически не гасим (закрытие отменило бы их); сертификат гасит сотрудник кнопкой. 
- Запись в истории: «Использован автоматически …». Комиссия начисляется как при ручном использовании.

## Тарифы PMS не сверяются

Решение владельца (19.10.2026): тарифы из PMS не нужны. Бронь проверяется по имени гостя, сроку заезда и числу ночей; тариф брони не читается и не влияет на расхождения. Столбец `pms_settings.certificate_rate_plan` в базе оставлен без использования.

## Услуги из PMS (Exely)

Решение владельца (19.10.2026): из PMS берётся **только список услуг** (тарифы и цены — нет; в справочнике Exely цен нет). Источник — Exely напрямую: Content API `GET /api/content/v1/properties/{propertyId}`, поле `services` (ID, название, вид, статус). Ключам Gifter нужен доступ к Content API (иначе запросить у Exely). Hotel Hub — позже, без проверки.

- **Ключ — ID услуги.** Название в PMS может быть на разных языках и меняться: запись обновляется по ID, дубля нет. Название услуги в Gifter берётся один раз при создании и дальше не перезаписывается (его можно переименовать или перевести).
- **Обновление:** `gifter:sync-pms-catalog` каждую ночь в 03:00 и кнопка «Обновить услуги из PMS» (Каталог → «Услуги PMS» и «Настройки PMS»).
- **Тумблер «Можно включать в сертификат»** (директор): создаёт услугу Gifter **без цены** — цену вводит директор, подтверждает администратор; пока цены нет, услуга не продаётся (плитка «Услуги без цены»). Выключение скрывает услугу из новых сертификатов. Уже существующую услугу Gifter можно связать с услугой PMS («Связать…»), чтобы не создавать дубль.
- **Пропавшие** в PMS помечаются, ничего не удаляется; связанная услуга Gifter перестаёт предлагаться в новых сертификатах и возвращается, если услуга снова появилась в PMS.
