Дата: 18.10.2026. Источник: архив «Old plans» (прислан владельцем). Репозиторий `gifter` на момент аудита пуст.

|---|---|---|
| `index.html` + `README.md` | Одностраничный прототип, данные в `localStorage` | Только образец интерфейса и сценариев, не код |

Проверено: `php -l` по всем файлам `app/`, `database/`, `routes/` — синтаксических ошибок нет. В локальной `database.sqlite` применены все 4 миграции. Каталога `vendor` в архиве нет, поэтому приложение и тесты не запускались. В `storage/logs/laravel.log` — ошибка генератора Filament (`make:filament-resource` для `payments`), из-за неё формы и таблицы трёх ресурсов остались пустыми.

## Найденные дефекты (важно для решения KEEP/MODIFY)

1. **Создание сертификата в панели не работает.** `CreateGiftCertificate` — обычный `CreateRecord`, `CertificateIssuer` не вызывается; поле `number` обязательное, но в форме отключено → вставка падает. Кроме того, в `GiftCertificateForm` написано `dehydrated(false())` — вызов несуществующей функции, форма падает при открытии.
2. **В панель никто не войдёт в production.** `User` не реализует `FilamentUser::canAccessPanel()`; Filament 4 вне `local` отказывает всем.
3. **Нет авторизации.** Роль — строка `users.role` (`viewer`/`administrator`), политик нет. OAuth Mail.ru не подключён (нет Socialite, нет маршрута callback), есть только колонки `provider`/`provider_id`.
4. **Сертификаты и связанные записи можно удалить.** `cascadeOnDelete` на `certificate_services`, `payments`, `certificate_history`; `DeleteBulkAction` на ресурсах клиентов, пакетов и платежей; `service_prices` удаляются вместе с услугой.
5. **Нумерация небезопасна.** Номер = `count()` сертификатов за год по `created_at` + 1 с `lockForUpdate` на агрегате: при параллельной продаже возможен дубль (спасает только unique-индекс ошибкой), год берётся из `created_at`, а не из даты продажи.
6. **Продажа и оплата смешаны.** `CertificateIssuer` сразу ставит `active` и создаёт платёж `paid` на полную сумму со способом по умолчанию `Kaspi QR`. Нет черновика, нет регистрации реального платежа.
7. **Покупатель и получатель — одна таблица, поиск по телефону.** `firstOrCreate(['phone'])`: разные люди с одним телефоном склеиваются, данные существующего клиента молча игнорируются.
8. **История неполная.** Пишется только событие `issued`; правка статуса, дат, состава и платежей через панель в историю не попадает. Таблица `activity_log` есть, но модели и записи в неё нет.
9. **Форма редактирования сертификата позволяет всё:** свободно менять статус (в т. ч. `used` → `active`), даты действия, дату продажи — без правил и без истории.
10. **Пароль по умолчанию в сидере** для `admin@tenir.kz` хранится в коде. В архиве также лежат `.env` с `APP_KEY`, `database.sqlite` и логи с локальными путями — в репозиторий не переносить.
11. **Тестов нет** — только `ExampleTest` из шаблона Laravel.

## Предлагаемый порядок фазы 1

1. Перенести каркас `tenir-mvp` в репозиторий (без артефактов из REMOVE), убедиться, что `composer install`, миграции и `php artisan test` проходят.
2. Заменить единую миграцию набором миграций по сущностям ядра (данных в production, судя по архиву, нет — см. вопрос 1).
3. Модели ядра, enum статусов, сервис переходов, история, аудит, запрет удаления, генератор номера.
4. Ресурсы Filament для ядра без удаления; создание сертификата только через сервис.
5. Тесты ядра.
